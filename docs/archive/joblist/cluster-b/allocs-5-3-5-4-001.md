## 5.4 — what the pool removes

One packet-struct allocation per forwarded copy: unpooled 1 allocs/op
(~168 B) → pooled 0 allocs/op, and ~230 → ~48 ns/op per copy
(~4.8x). The CSRC packet keeps 1 allocs/op pooled — that alloc is
`Header.Clone()` copying the CSRC slice, not the struct; the pool
cannot remove it (see below).

At scale the saving is per fan-out, not per packet: one packet fans
out to N viewers, so N copies. At 5,000 viewers per publisher,
unpooled = 5,000 struct allocs per packet (~840 KB/packet); pooled =
0. At 5 fps × 20 publishers = 100 packets/s, unpooled ≈ 500,000
struct allocs/s; pooled ≈ 0.

Latency (the "no p99 increase" half): enqueue ns/op is the
in-process latency proxy — pooled ~499 ns/op vs unpooled ~539 ns/op:
no increase (pooled is slightly faster, within noise). Viewer-side
p99 at scale is a Mac-run gate, not measurable in-process; the
in-process claim is exactly "the pool does not slow the enqueue
path", which the ns/op comparison supports.

Mechanism (new, test-only): package var
`disableRTPPacketCopyPool` (default false; benchmarks set it and
defer-restore it; never set in production) makes
`copyRTPPacketWithSharedPayload` allocate a fresh struct instead of
a pool Get. New benchmarks: `BenchmarkCopyRTPPacketUnpooled`,
`BenchmarkCopyRTPPacketVideoShape`,
`BenchmarkCopyRTPPacketVideoShapeUnpooled`,
`BenchmarkEnqueueRTPUnpooled`.

## 5.3 — why no copy was reduced

`copyRTPPacketWithSharedPayload` does two things: a struct copy
(`*packetCopy = *packet`, a memcpy, no alloc) and
`Header.Clone()`. Pion v4.2.26's `Clone` (`rtp@v1.10.6/packet.go:589`)
allocates ONLY when CSRC or Extensions are non-nil — for the real
video packet (no CSRC, no extensions) it is allocation-free, which
the video-shape benchmark confirms (0 allocs/op pooled). The struct
copy itself is required: each viewer needs its own mutable header
because Pion copies the packet struct before mutating the per-binding
RTP header on write — sharing one struct across viewers would
corrupt that. `rememberPacket` stores the pointer (no copy); the
shard path shares one copy across its subscriptions. There is no
further copy in our code to remove. The before/after above IS the
reduction: the pool (already landed) is what removes the struct
alloc, and 5.4 measures it.

The CSRC packet's remaining 1 allocs/op is `Clone()` copying the
CSRC slice. Real forwarded video packets carry no CSRC, so this is a
benchmark-shape artifact, not a forward-path cost. (If a future
packet shape ever carries CSRC per viewer, that alloc returns — the
existing CSRC benchmark is the trip wire.)
